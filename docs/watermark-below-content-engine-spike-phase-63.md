# LiftPDF Phase 63 - True Below-Content Watermark Engine Spike

Date: 2026-08-11  
Scope: engine spike only. No `/watermark-pdf` runtime behavior changed.  
Commit baseline: `1437204 Document remaining PDF engine feasibility`

## 1. Technical Question

Can LiftPDF, with the current architecture:

- `pdf-lib`
- low-level PDF object access
- no new dependency
- no backend

add a real below-content watermark by inserting a new content stream before each original page content stream?

The required structural condition is:

```text
/Contents [watermark original1 original2 ...]
```

and not:

```text
/Contents [original1 original2 watermark]
```

The watermark must be painted before original page content, not simulated with opacity, blend modes, rasterization, or an overlaid pseudo-background.

## 2. Current Architecture

Current Watermark PDF uses `pdf-lib` high-level drawing:

- `page.drawText(...)`
- `page.drawImage(...)`

That path appends drawing operations to the page content, producing a reliable above-content watermark. Phase 62 classified true below-content as `PARTIAL` because production code had not proven low-level stream insertion across multiple page structures.

Phase 63 tested a separate spike outside runtime:

```text
scripts/spikes/phase63-watermark-below/run.mjs
```

The script is not imported by any route or production component.

## 3. PDF Content-Stream Model

The spike handles `/Contents` as:

- missing;
- a single reference/stream;
- an array of references;
- an existing array with empty streams;
- pages with direct or indirect `/Resources`.

The production-ready strategy would normalize each targeted page to a `/Contents` array and prepend a new registered stream:

```text
Before:
/Contents [6 0 R]

After:
/Contents [8 0 R 6 0 R]
```

The spike uses only object-model APIs. It does not search or replace raw PDF bytes.

## 4. Strategies Tested

| Strategy | Description | Result |
|---|---|---|
| STRATEGY_A | Separate prepended watermark content stream | PASS |
| STRATEGY_B | Isolate watermark state with `q ... Q` | PASS |
| STRATEGY_C | Low-level `/Contents` array manipulation | PASS |

| Rasterization | Not used | Rejected by design |

## 6. Structural Results

Every generated below-content output passed:

- PDF parsing with `pdf-lib`;
- page count preservation;
- `/Contents` array with watermark stream first;
- original content stream references preserved after the watermark stream;
- resource dictionary preserved;
- new resource names allocated without collision;
- annotation arrays preserved where present;
- targeted-page simulation modified only targeted pages.

Example output from F1:

```text
Original /Contents refs:
[6 0 R]

Below-content /Contents refs:
[8 0 R, 6 0 R]

watermark_first = true
```

## 7. Pixel-Level Results

The spike rendered original, above-content, and below-content variants using PDF.js under Chromium and Firefox through Playwright.

The key occlusion test uses an opaque black rectangle in the original page content:

- Above-content watermark: changes pixels inside the black rectangle.
- Below-content watermark: does not change those pixels because the original black rectangle covers it.

Representative results:

| Browser | Fixture | Above changed pixels in occlusion region | Below changed pixels in occlusion region | Verdict |
|---|---|---:|---:|---|
| Chromium | F2 IMAGE_HEAVY | 1756 | 0 | PASS |
| Chromium | F3 MULTIPLE_CONTENT_STREAMS | 1756 | 0 | PASS |
| Chromium | F6 CLIPPING | 1756 | 0 | PASS |
| Firefox | F2 IMAGE_HEAVY | 1664 | 0 | PASS |
| Firefox | F3 MULTIPLE_CONTENT_STREAMS | 1664 | 0 | PASS |
| Firefox | F6 CLIPPING | 1664 | 0 | PASS |

The rotated-page check uses rotation-adjusted visual comparison because the occlusion box maps to a rotated canvas coordinate system. It passed in Chromium and Firefox.

## 9. Resources

The transformer adds watermark resources without replacing original resources:

- text watermark adds a unique font name and ExtGState;
- image watermark adds a unique XObject name and ExtGState;
- existing `/Font`, `/XObject`, `/ExtGState`, and indirect `/Resources` are preserved;
- collision fixture with existing `LPGS1` allocates another safe resource name.

Result:

```text
RESOURCES_PRESERVED = YES
```

## 10. Graphics State

The watermark stream is wrapped:

```text
q
...
Q
```

This isolates:

- current transformation matrix;
- alpha / ExtGState;
- color;
- text state;
- font state;
- image transform.

Because the inserted stream closes its own graphics state, original content does not inherit the watermark alpha or transform.

Result:

```text
GRAPHICS_STATE_ISOLATION_VERIFIED = YES
```

## 17. Signed PDF Implications

Any PDF modification changes bytes and normally invalidates existing cryptographic signatures. The spike did not attempt to preserve signatures.

Future production handling:

- detect signatures if feasible;
- warn or block below-content watermarking for signed PDFs;
- never imply signature preservation.

Result:

```text
SIGNED_PDF_MODIFICATION_INVALIDATES_SIGNATURE = YES
```

## 20. Detectable Limitations

Acceptable limitations:

| Limitation | Status | Production behavior |
|---|---|---|
| Encrypted PDFs | DETECTABLE | Keep current "unlock first" flow. |
| Signed PDFs | DETECTABLE / WARNABLE | Warn or block because modifications invalidate signatures. |
| Annotation/widget visual order | TECHNICAL WORDING LIMITATION | Say "below page content", not "below every visible object". |
| Parser-accepted but unusual PDFs | FAILURE_SAFE_REQUIRED | Future helper returns unsupported instead of writing uncertain output. |

Non-acceptable limitations were not observed in the spike:

- watermark appended above original content;
- original streams reordered;
- resources overwritten;
- forms lost;
- links lost;
- invalid PDF output;
- browser-specific rendering failure.

## 21. Failure-Safe Strategy

A production helper should:

1. Load the PDF with `pdf-lib`.
2. For each targeted page, inspect `/Contents` and `/Resources`.
3. Allocate collision-free resource names.
4. Register a watermark stream.
5. Prepend it to a normalized `/Contents` array.
6. Save.
7. Re-open output and verify:
   - page count;
   - watermark stream first;
   - original refs preserved;
   - target pages modified;
   - non-target pages unchanged structurally where possible.
8. If verification fails, return `UNSUPPORTED_BELOW_CONTENT_WATERMARK`.

No UI should show success before verification.

Ready for production implementation:

Required production constraints:

- use a dedicated low-level helper, not ad hoc logic inside the React component;
- keep above-content as the default;
- expose below-content with clear wording;
- verify output before success;
- warn/block signed PDFs if signature detection is implemented;
- keep encrypted PDFs in the existing Unlock PDF path;
- document that annotations/widgets may render above page content.
